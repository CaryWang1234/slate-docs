AI 团队与工作流

一个人（哪怕是一个模型）想不到的地方，往往要靠另一个立场的角色来挑。团队模式让多个角色围绕同一议题多轮辩论，最后交出一份带拍板结论的摘要；工作流模式则把长任务拆成有依赖关系的节点，能并行的并行跑完。

#AI 团队解决什么

它的价值不在「多几个声音」，而在对抗：让一个角色负责务实、一个负责创新、一个负责拍板，观点互相顶一下，你拿到的不再是第一反应的答案，而是被质疑过一轮的答案。

适合的议题：方案取舍、技术选型、风险排查、产品方向、需要正反两面都看到的决定。

#辩论怎么进行

在「对话」工作区标题栏左侧把模式从「对话」切到「团队」，就进入团队讨论视图：

  1. 选一套团队预设，或自己配成员。
  2. 在议题输入框写下要讨论的问题。
  3. 选辩论轮数（默认 5 轮，可切 3 / 5 / 8 / 10 轮）。
  4. 点「开始讨论」，各成员按顺序发言。

第一轮每位成员各自提案。之后每一轮，成员可以看到全部已有发言，选择提案、支持、反对、反驳或补充，也可以点名回给某位成员。整个过程按轮次逐条铺开，你随时能看到谁说了什么。

#发言的六种动作

每一句发言都以一个动作开头，系统据此分类，摘要里的发言统计也来自这里：

动作含义
【提案】提出新想法或新方案
【支持】认同并强化某个已有观点
【反对】明确不认同某一观点
【反驳】针对某个观点的论证过程给出反驳
【补充】在同一方向上补上被漏掉的部分
【决策】给出最终方案，讨论就此结束

要定向回应某个人，在动作后写 @成员名，例如 【反驳】@性能专家 这个结论忽略了冷启动成本。系统会把它记成一条指向对方的回应边。

每次发言都被要求简短（一到三句），既是为了读起来是辩论而不是论文，也是为了省 Token。

#角色与模型分工

默认三位成员对应三种立场：

角色立场职责
分析师务实关注可行性与成本
创意者创新关注可能性与用户体验
决策者综合汇总各方观点，给出最终方案与理由

只有决策者能拍板：其他成员即使写了【决策】也会被当成普通提案。决策者可以在任意一轮直接给【决策】收口结束讨论；如果轮次用尽仍无共识，会由决策者再补一轮最终决策。

模型分工是刻意设计的：讨论位用轻量模型，决策位用重型模型。讨论阶段发言次数多但每句都短，用轻量模型足够；最终方案只出一次，值得用更强的模型。

轮次越多越费 Token

每一轮里每位成员都要把已有的全部发言读一遍。轮数乘以人数，成本是相乘的。三到五轮通常就能看出分歧在哪，把角色数量控制在真的需要的范围。

#自定义团队

把预设当起点，逐张成员卡改就行：

  • 名称：直接改卡片上的名字，辩论记录里就用这个名字（@ 回应也认它）。
  • 模型：每张卡上选模型，可按「国外 / 国内 / 本地 / 自定义」分组挑。没配 Key 的模型会标注提示。
  • 人设：卡上的角色设定文本就是这位成员的立场与风格，改它等于重新定义这个角色。
  • 专家包：每张卡可选一个专家包，把人格与规则绑到这个角色上，见 专家包。
  • 增删：顶部「＋」添加成员，卡片右上角「×」移除。自己加进来的成员默认是普通成员，不参与拍板。

想让某位成员负责拍板，用预设里的决策者位，或把成员改成决策者位再调整人选。

#决策等你拍板

「决策需我拍板」默认开着：决策者给出【决策】之后，这场讨论不自己收口，而是停下来等你签字。

  • 采纳拍板：以那条决策结束，摘要照常生成。
  • 继续讨论，或者不选直接关掉弹窗：算「没签」，讨论带着「未拍板」往下再辩一轮，下一位的提示词里会写明这条决策还没被签字。
  • 重开有次数上限，用尽后讨论自行收口——每一轮重开是全员再发言一次，不给它无限烧下去的口子。

拍板那一行是讨论里的一笔独立记录：它进下一位的上下文、进后端记录，但不算任何一位成员的发言，星图也不会把它数成谁的观点。

夜间模式（全托管）下不弹窗打断，决策直接采纳，但那一行照样画出来并写明是自动采纳——不会读成你点过头。不想被拦就在团队面板取消那个勾选，回到「决策即结束」。

#讨论摘要与收尾

讨论结束时会自动生成一份「辩论摘要」，包含：

  • 议题与参与成员名单。
  • 发言统计：共几条，以及提案 / 支持 / 反对 / 反驳 / 补充 / 决策各多少条。
  • 最终方案与提出者；如果始终没有形成决策，则明确写「未达成明确决策」。

摘要之外，整场辩论的逐条发言也留在讨论区里，可以往下翻看。

#中途停止

点「停止讨论」即可中断。已完成的发言原样保留，不会因为停止而丢掉已经辩出来的成果。

被手动停止的这一场不生成摘要——没有结论就不编一个结论；但它照旧进团队历史，那一行标着「已中断」，点开看得见已经辩完的那几段。

#失败与缺席不算发言

某位成员这一轮请求失败，或他绑的模型没配 API Key，那一格会明确标「失败」/「未参与」：

  • 这句报错不会进下一位的上下文——否则模型会把一条报错当成某人的主张接着反驳。
  • 它不计入发言统计，星图里那位成员的发言数就是 0。
  • 后端仍留一行 error / skipped，事后能追溯谁在哪一轮没说话；这两种状态也只能由系统标出，模型写【失败】是解析不出来的。

#切走了也找得回来

辩论在你切到「对话」面板的这段时间继续跑。等你签字与这场收口，都会进右侧的任务中心，与后台终端任务、子代理批次排在同一张表里：那一行写着议题，等签字时标「等你拍板」，点行上的团队按钮跳回这一场重看，点停止中断的也正是这一场。

#讨论记录去哪了

每次发言会同时落两个地方：

  • 本机历史：左侧「团队历史」列表，保留最近 50 场，列出时间、发言条数与大致 Token 用量，点一条即可回看。
  • 后端团队会话：一场讨论对应一份会话记录、一份成员名册，以及每位成员各自一次事件账本记录。

后端那份是黑板 · 工作流视图里「团队星图」的数据源：按角色摆出最近一次讨论，谁回应了谁、谁动过哪些工具、谁派生了子代理，全部取自真实记录。如果写入后端失败，本机历史仍在，那条列表会标上「仅本机记录」；这场对话完全没有团队记录时，星图会直说，不会画一张装饰性的图。星图的读法见 白板式逻辑链。

#团队工作流：把流水线交给 DAG

辩论是「一起想」，工作流是「分头干」。切到团队面板的「工作流」页签：

  1. 选一套工作流模板。
  2. 在下面填任务需求，它会作为 $input 传给各个节点。
  3. 点「运行工作流」。

节点之间靠依赖边串起来：上游产出可以作为下游的输入（$node_id 形式引用），没有依赖关系的节点会同时执行。每个节点跑起来后状态实时回显——等待、运行中、成功、失败、跳过；某一个节点失败或被跳过，依赖它的下游会自动跳过，而不是带着空输入硬跑。运行中可以随时点停止，未开始的节点会标为跳过。

节点的模型绑定按这个优先级取：绑定团队成员的角色（沿用它的模型与人设）→ 节点自己指定的模型 → 「设置 → AI 辅助功能」里「工作流」那一档指定的模型 → 当前模型。

整条流水线跑完，产物会自动归档进知识库，标题形如「工作流产物 · 模板名」，可在记忆面板里查看。

#内置工作流模板

SLATE 自带 8 套模板：

模板节点流水线
标准开发流程需求分析 → 任务拆解 → 编码实现 → 代码审查 → 总结交付
并行研究分析需求分析 → 技术调研 / 风险评估 / 资源评估 → 汇总决策
代码审查流程变更扫描 → 质量审查 / 安全审查 / 性能审查 → 汇总报告
文档生成流程大纲规划 → 正文撰写 → 摘要提炼 → 交付整合
数据分析流程数据理解 → 趋势分析 / 异常检测 → 统计摘要 → 决策建议
研究报告流程课题定义 → 背景调研 → 方案对比 / 可行性分析 → 报告生成
产品需求流程想法梳理 → 用户故事 → 功能拆解 → 优先级排序 → 需求文档
Bug 排查流程Bug 描述 → 日志分析 / 代码分析 / 环境分析 → 根因定位

#工作流的导入、导出与删除

工作流模板以 JSON 定义文件形式提供，含节点、依赖边与每个节点的提示词。其中「标准开发流程」与「并行研究分析」是内置模板，不可删除；其余自定义模板可以导入、导出与删除。删除只在模板层面生效，已经跑出来的产物仍留在知识库里。
